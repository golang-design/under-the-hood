# 写作公约

本文约定《Go 语言原本》怎么写。动笔或修订任何一节之前先读一遍。
实现细节以 Go 1.26 为准（参考检出 `release-branch.go1.26`），涉及版本差异时写明版本号。

## 一、为谁写，写到什么程度

读者会写程序，学过数据结构，但不一定读过运行时源码，也不一定读过相关论文。

读完一节，读者应当能说清五件事：

1. 这里要解决什么问题；
2. 直觉上怎么解；
3. 背后的理论是谁、在什么背景下提出的，为什么成立；
4. Go 具体怎么做，换来了什么，付出了什么；
5. 怎样亲手验证上面这些说法。

「深」指推理链条完整、信息密度高，不指篇幅长。能用一句话讲清的不写三句；
一段只讲一件事。

## 二、一节的骨架

下面的顺序是默认值，可以按内容调整，但不要跳过「直觉」直接进入术语和源码。

1. **问题**：用一个具体场景、一个数字或一段可运行的程序把问题摆出来。
2. **直觉**：用日常经验或最小的例子讲清核心想法。这一步尽量不引入新术语，最多引入一个。
3. **理论与来历**：谁、哪一年、为了解决什么问题提出了这个想法；关键结论是什么；
   用最少的形式化把它说准（一条公式或一个定义就够）；它在 Go 里适用到哪里为止。
4. **Go 的做法**：把想法对应到 Go 1.26 的实现。源码里的名字从这里才开始出现。
5. **动手**：可运行示例、交互图，或一条读者能在自己机器上敲的命令。
6. **取舍与演进**：换来什么、付出什么；历史上改过什么，为什么改。
7. **延伸阅读**：带一句说明的文献列表（见第六节）。

## 三、语言

### 概念怎么引入

- 先说它**做什么**（一句白话），再给**名字**（中文名加英文原词），需要时再给**定义**。
  例：「每个线程都需要随时知道自己正在运行哪个 goroutine。操作系统为此给每个线程留了
  一小块私有存储，叫线程本地存储（thread-local storage，TLS）。」
- 一个概念全书只用一个中文名，以 [术语表](zh-cn/glossary.md) 为准。新增术语时同步更新术语表。
- 源码标识符（`g0`、`stackguard0`、`heapLive`）只在概念讲清之后出现，
  并就地说明它对应哪个概念。不要让标识符替正文承担解释。
- 缩写首次出现时给全称：TLS、ABI、SSA、DAG、ELF。
- 「goroutine」一律小写，与 Go 官方文档一致；标题里也一样。

### 文风：专业的书面语

本书是技术专著，用规范的书面语写作，语气平实、克制、准确。可以参照《深入理解计算机系统》
《程序员的自我修养》中文版的文字。

- 使用领域内通行的中文术语。首次出现时加粗并附英文原词，用一个分句说明它指什么。不为了
  「通俗」自造说法；没有通行中文译名的，保留英文。
- 不解释读者已经掌握的基础概念：寄存器、线程、哈希函数、栈与堆等。读者是有计算机基础的
  Go 程序员。
- 不用生活化的比喻代替概念（穿衣、排版、菜谱之类）。经典文献里的标准例子（如哲学家就餐）
  可以用。
- 不用口语词：好办、麻烦、干活、随手、看一眼、一下、就行、拿来、弄、说白了、吧、呢、啥、挺。
- 句子完整，用连接词交代逻辑关系（因此、由于、然而、从而），不写一连串零碎的短句。
- 引用的名言、标题若已有通行的中文译法，沿用通行译法（先查证）。
- 加粗只用于术语首次出现。

常见替换：

| 避免 | 改用 |
| --- | --- |
| 填空、留个条子 | 重定位、重定位项 |
| 附加信息（内核放在栈上的） | 辅助向量（auxiliary vector，auxv） |
| 运行 Go 代码的许可 | 处理器（P） |
| 存表的做法 | 以输入摘要为键、记录输出的缓存 |
| 步骤图 | 动作图（action graph） |
| 干活 | 工作、执行 |
| 好办 / 麻烦 | 直接 / 复杂 |
| 先看两个小问题 | 先看两个例子 |

### 人称与标点

- 以「我们」与读者同行；需要指读者时写「读者」，不写「你」。表达作者个人观点时用「笔者」。
- 不使用破折号（`——`、`—`）。补充、转折用逗号、冒号、括号或另起一句。
- 中文句子使用全角标点。中文句子里不得出现半角逗号。
- 中文与英文、数字之间加一个空格。
- 数值范围写「2 至 3」，不写「2~3」（单个 `~` 会被 Markdown 渲染成删除线，CI 会拦截）。
- 引号用「」，嵌套用『』。

### 英文版

英文版不逐句翻译中文版。按英文母语读者的习惯重写：结构、图、示例、文献保持一致，
句子和措辞按英文的方式组织。避免中式英文，也避免英文里同样费解的行话。

## 四、代码

本书有三类代码，各有规矩。

**可运行示例**（读者可以直接运行或修改）：

````markdown
```go {run=true}
package main
...
```
````

- 完整的 `package main`，只依赖标准库，几十行以内。
- 输出要确定。不要依赖 goroutine 的调度次序，除非这正是要演示的现象。
- 正文写出预期输出，或说明输出中哪一部分会随机器变化。
- 网站上的运行环境是浏览器里的 js/wasm（单线程，`GOMAXPROCS` 实际为 1，没有信号和网络）。
  只有在真实操作系统、多核上才能复现的示例，加 `native=true`，网站会提示读者到
  go.dev/play 或本机运行。
- 需要环境变量的，写 `env="GODEBUG=inittrace=1"`。
- 提交前用 `go run` 在本机验证过输出。

**源码速写**（帮助读者理解实现）：

- 裁剪到只剩与设计有关的几行，注释说明每一行为什么存在。
- 注明出处：符号名加文件路径（如 `runtime.schedinit`，`runtime/proc.go`）。
- 不整段粘贴函数体，不逐行翻译源码注释，不照搬几十个字段的结构体。

**伪代码**：讲算法骨架时用，十几行以内，比散文更清楚时才用。

判断标准只有一条：这段代码是否让读者更快理解了某个机制或某个设计决定。

## 五、图

本书有三种图：

- **Mermaid**：结构、流程、状态机、时序。统一用 ` ```mermaid ` 围栏代码块，
  GitHub 与网站都能渲染。渲染后要实际看一眼（`mmdc` 或网站预览），确认没有挤压、错位。
- **交互图**：只有「动起来」或「亲手调参数」才容易理解的机制，例如调度、标记、初始化次序、
  寄存器分配。嵌入写法：

  ```html
  <div class="viz" data-viz="init-order"></div>
  ```

  组件代码放在 `website/themes/book/static/viz/widgets/<name>.js`，接口见
  `website/tools/viz/README.md`（可用 `website/tools/viz/harness.html` 单独预览、截图）。
- **表格**：并列比较。

交互图的要求：

- 一张图只讲一个机制。默认状态下就能看出要点，读者可以单步、重放、调参数。
- 图前后的文字必须自足：GitHub、PDF 和 EPUB 的读者看不到交互图。
- 标签同时提供中英文（组件按页面语言选择）。配色取站点的 CSS 变量，深浅色都要清楚可读。
- 不依赖第三方库，不发起网络请求。

## 六、理论与文献

讲一个理论时交代：谁、哪一年、当时想解决什么问题、核心想法的直觉、关键结论
（必要时一条公式）、Go 用了其中哪一部分、哪一部分在 Go 里不成立或不需要。

节末「延伸阅读」的格式：

```markdown
1. C. A. R. Hoare. "Communicating Sequential Processes." *Communications of the ACM*,
   21(8): 666–677, 1978. https://doi.org/10.1145/359576.359585
   CSP 的第一篇论文。进程按名字直接通信，还没有 channel。
```

- 作者、标题、出处、年份，有 DOI 给 DOI，否则给稳定的 URL。每条后面一句话说明它和本节的关系。
- 一手资料（论文、提案、设计文档、作者文章、源码）优先于二手转述。
- 只引用确定存在的文献。拿不准的链接宁可不给，只给完整的书目信息。
- 本书内部的交叉引用写在正文里，不放进延伸阅读。

## 七、机械规则

- 保留每个 `.md` 顶部的 Hugo frontmatter（`weight`、`title`、`bookCollapseSection`），
  它们决定网站目录。
- 一次提交只做一件事，提交信息写清做了什么、为什么。
